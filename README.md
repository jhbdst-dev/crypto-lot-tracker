# 프로젝트 소개

crypto-lot-tracker는 업비트 API와 연동하여 암호화폐 자산을 관리하는 웹 애플리케이션입니다.

거래내역을 기반으로 코인별 자산 현황과 개별 거래 손익을 계산하고, 예상 매도 결과를 확인할 수 있습니다.

백엔드는 Python과 FastAPI, 프론트엔드는 React와 TypeScript를 사용하여 개발했습니다.

# 프로젝트를 만든 이유

업비트에서는 같은 코인을 여러 번 매수하면 평균 매수가만 제공되기 때문에,
각 거래별 손익과 수익률을 확인하기 어렵다는 불편함이 있었습니다.

이러한 불편함을 해결하기 위해 거래내역을 직접 분석하여
개별 거래의 손익과 수익률을 계산하고,
예상 매도 결과까지 한눈에 확인할 수 있는 프로젝트를 만들게 되었습니다.

# 주요 기능

### 자산 현황 조회

업비트 API에서 보유 자산과 현재가를 가져와 총 평가금액, 총 매수금액, 평가손익, 수익률을 계산합니다.

### 코인별 상세 정보 조회

보유 중인 코인별로 보유수량, 평균 매수가, 총 매수금액, 평가금액과 평가손익을 확인할 수 있습니다.

### 개별 매수 거래 추적

거래내역을 기준으로 각 매수 거래의 매수가, 매수원금, 남은 수량, 평가손익과 수익률을 계산합니다.

### 예상 매도 결과 계산

매도 예정가와 수량을 입력하면 예상 매도금액, 수수료, 정산금액, 실현손익과 수익률을 미리 확인할 수 있습니다.

### 거래내역 저장 및 중복 방지

업비트에서 가져온 거래내역을 PostgreSQL에 저장하며, 거래 UUID를 기준으로 중복 저장을 방지합니다.

# 기술 스택

### Backend

- **Python**: 거래내역 처리 및 손익 계산 로직 구현
- **FastAPI**: 계산 결과를 프론트엔드에 전달하는 API 서버 구성

- **React**: 자산 현황, 코인 상세, 예상 매도 화면 구성

- **Git / GitHub**: 버전 관리 및 프로젝트 저장소 관리
- **GitHub Desktop**: 변경사항 확인 및 커밋 관리

# 백엔드 구조

백엔드는 FastAPI를 중심으로 구성하였으며, API 요청을 받아 업비트 API와 PostgreSQL의 데이터를 조회한 뒤
필요한 계산을 수행하여 JSON 형태로 프론트엔드에 전달합니다.

```text
backend/

├── api.py               # FastAPI API 엔드포인트
├── calculator.py        # 자산 및 손익 계산
├── database.py          # PostgreSQL 데이터 조회 및 저장
├── upbit_api.py         # 업비트 거래내역 조회
├── upbit_accounts.py    # 업비트 보유 자산 조회
├── upbit_prices.py      # 업비트 현재가 조회
```

| 파일                  | 역할                                                         |
| --------------------- | ------------------------------------------------------------ |
| **api.py**            | FastAPI 엔드포인트를 제공하고 프론트엔드 요청을 처리합니다.  |
| **calculator.py**     | 자산, 평가금액, 손익, 수익률 등 핵심 계산 로직을 담당합니다. |
| **database.py**       | PostgreSQL에서 거래내역을 저장하고 조회합니다.               |
| **upbit_api.py**      | 업비트 API를 호출하여 거래내역을 수집하고 DB에 저장합니다.   |
| **upbit_accounts.py** | 업비트 계좌의 보유 코인, 보유수량, 평균 매수가를 조회합니다. |
| **upbit_prices.py**   | 보유 코인의 현재 시세를 조회합니다.                          |

# 어려웠던 점과 해결 과정

프로젝트를 개발하면서 가장 어려웠던 점은 단순히 기능을 구현하는 것이 아니라,
실제 데이터를 기반으로 프로젝트 구조를 계속 수정하고 개선해야 했다는 점이었습니다.

---

## 1. 가상 데이터에서 실제 API 데이터로 구조 변경

### 문제

초기에는 직접 만든 가상 거래 데이터를 사용하여 프로젝트를 개발했습니다.

하지만 실제 업비트 API를 연동하면서 데이터 구조와 필드 구성이 예상과 달랐고,
기존 계산 로직으로는 실제 거래 데이터를 정확하게 처리할 수 없었습니다.

### 해결

프로젝트 구조를 실제 업비트 API 응답에 맞게 다시 설계했습니다.

거래내역 저장 방식과 계산 로직을 수정하여
실제 거래 데이터를 기반으로 동작하도록 변경했습니다.

---

## 2. FastAPI 도입에 따른 프로젝트 구조 변경

### 문제

초기에는 터미널 출력 중심으로 프로젝트를 개발했습니다.

하지만 React 프론트엔드와 연동하기 위해서는
계산 결과를 화면에서 사용할 수 있는 형태로 전달해야 했고,
기존 구조로는 프론트엔드와 효율적으로 연동하기 어려웠습니다.

### 해결

FastAPI를 도입하여 API 서버를 구성하고,
화면에서 필요한 데이터를 JSON 형태로 반환하도록 구조를 변경했습니다.

계산과 출력을 분리하여
프론트엔드와 백엔드의 역할을 명확하게 나누었습니다.

---

## 3. 거래내역만으로 현재 보유 수량 계산

### 문제

업비트 거래내역에는 입금과 출금 내역이 포함되지 않기 때문에,
거래내역만으로 현재 보유 수량을 계산하면 실제 보유 자산과 일치하지 않는 문제가 있었습니다.

특히 이더리움은 외부 지갑으로 입출금한 이력이 있어
거래내역만으로는 현재 보유 수량을 정확하게 계산할 수 없었습니다.

### 해결

거래내역을 다시 분석하여 계산 방식을 변경했습니다.

매도 후 보유 수량이 **0이 되는 시점을 하나의 거래 사이클 종료**로 판단하고,
이후 새로운 매수가 발생하면 새로운 거래 사이클을 시작하도록 계산 로직을 구현했습니다.

이를 통해 현재 보유 중인 거래만 추적할 수 있도록 개선하였고,
입출금 이력이 있는 경우에도 안정적으로 데이터를 계산할 수 있었습니다.

---

## 4. 화면 중심으로 백엔드 재설계

### 문제

처음에는 계산 로직을 중심으로 백엔드를 구현했습니다.

하지만 React 화면을 개발하면서
실제 화면에서 필요한 데이터 구조와 백엔드에서 제공하는 데이터 구조가 달라
여러 번 수정이 필요했습니다.

### 해결

화면에서 필요한 데이터를 먼저 정의한 뒤,
FastAPI가 해당 형태의 JSON을 반환하도록 API를 다시 설계했습니다.

이를 통해 프론트엔드와 백엔드의 역할을 명확히 분리할 수 있었고,
유지보수하기 쉬운 구조로 개선할 수 있었습니다.

# 프로젝트 발전 과정

### 1. 가상 데이터를 이용한 기능 구현

프로젝트 초기에는 실제 거래 데이터를 사용할 수 없어 최소한의 거래 데이터를 직접 DB에 저장했다.

매수 금액과 매수 수량만 저장하고, 현재가, 매도 가격, 매도 수량, 수수료율 등은 모두 변수로 관리하여 다양한 거래 상황을 직접 계산할 수 있도록 구현했다.

이를 바탕으로 수수료, 정산 금액, 평균 매수가, 평가 손익, 예상 매도 손익 등을 계산하는 로직을 구현하며 계산 과정을 하나씩 검증했다.

### 실제 데이터의 필요성

가상 데이터를 통해 계산 로직을 검증할 수 있었지만, 실제 거래 환경의 데이터 구조와는 차이가 있었다.

실제 거래 내역에는 체결 가격, 체결 수량, 수수료, 체결 시간 등 더 구체적인 정보가 포함되어 있었고, 현재가는 별도의 시세 데이터로 받아야 했다.

이에 따라 모든 값을 가정하여 계산하는 구조에서 벗어나, 실제 데이터를 가져와 필요한 값만 계산하는 방향으로 프로젝트를 발전시키기로 했다.

↓

### 2. Upbit API 연동

계산 로직을 검증한 후, 실제 거래 데이터를 가져오기 위해 Upbit API를 연동했다.

이를 통해 가상 데이터가 아닌 실제 거래 내역을 기반으로 보유 수량과 손익을 계산하도록 구조를 변경했다.

↓

### 3. PostgreSQL 저장

API로 가져온 거래 내역을 매번 다시 요청하는 대신, PostgreSQL에 누적 저장하도록 구조를 변경했다.

거래 데이터를 중복 없이 관리하고, 저장된 내역을 기반으로 보유 수량과 손익을 안정적으로 계산할 수 있도록 했다.

↓

### 4. 터미널 출력으로 계산 검증

계산 결과가 올바른지 확인하기 위해 모든 데이터를 터미널에서 출력하며 검증했다.

이 단계에서는 UI보다 계산 로직의 정확성을 우선으로 개발했다.

↓

### 5. React UI 제작

계산 결과를 사용자가 한눈에 확인할 수 있도록 프론트엔드를 구현했다.

필요한 데이터가 무엇인지 화면을 먼저 만들면서 다시 설계하게 되었다.

이 과정에서 프론트엔드가 사용할 데이터 형태를 새롭게 정의하게 되었고, 이후 FastAPI를 도입하는 계기가 되었다.

↓

### 6. FastAPI 도입

React 프론트엔드와 백엔드가 데이터를 주고받을 수 있도록 FastAPI를 도입했다.

기존 계산 로직을 API 엔드포인트와 연결하여, 화면에서 필요한 데이터를 요청할 수 있는 구조를 만들었다.

↓

### 7. JSON API 기반으로 변경

기존 터미널 출력은 사람이 결과를 확인하기 위한 문자열 중심의 방식이었다.

이를 코인별 보유 수량, 평가금액, 손익 등 프론트엔드가 사용할 수 있는 JSON 응답 구조로 변경하고 React와 연결했다.

↓

### 8. 코드 리팩터링

프로젝트가 완성된 이후에는 기능 추가보다 코드 이해와 구조 개선을 목표로 리팩터링을 진행하고 있다.

이를 통해 프로젝트를 완전히 내 것으로 만들고, 이후 ROS 프로젝트에서도 같은 방식으로 설계하고 개발할 수 있는 역량을 키우고 있다.

# 프로젝트를 하며 배운 점

이번 프로젝트를 진행하면서 가장 크게 배운 점은 **좋은 프로젝트는 처음부터 완성된 설계로 시작되는 것이 아니라, 요구사항과 데이터를 이해하면서 계속 개선된다는 것**이었습니다.

처음에는 가상 데이터를 기반으로 프로젝트를 개발했지만, 실제 업비트 API를 연동하면서 데이터 구조가 달라졌고, React와 FastAPI를 연결하는 과정에서도 여러 번 구조를 수정해야 했습니다.

처음에는 계산 로직 중심으로 개발했지만, 프로젝트가 완성될수록 **화면에서 필요한 데이터를 먼저 정의하고, 그에 맞춰 API와 백엔드를 설계하는 방식**이 유지보수와 확장성 측면에서 더 효율적이라는 것을 배울 수 있었습니다.

또한 실제 금융 데이터를 다루면서 **데이터를 정확하게 이해하는 것이 코드를 작성하는 것보다 더 중요하다**는 점도 배웠습니다. 거래내역, 수수료, 정산금액 등 각 데이터의 의미를 정확히 파악해야 올바른 계산 로직을 구현할 수 있었고, 단순히 기능을 구현하는 것이 아니라 데이터 자체를 분석하는 과정의 중요성을 경험했습니다.

이번 프로젝트를 통해 기능 구현뿐만 아니라 프로젝트를 설계하고 개선하는 과정, 실제 데이터를 분석하는 과정, 프론트엔드와 백엔드를 연결하는 과정을 모두 경험할 수 있었습니다.
